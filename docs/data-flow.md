# Data Flow — Raw Logs → Training Data (PDP Similar Items)

At a very general level, here's how the pipelines keep a fresh model in production:

First, a model goes into production, and the serving pipeline starts delivering predictions.

The data pipeline immediately begins collecting data to generate new training and test datasets, and stores it in a data warehouse.

Based on a schedule or a trigger, the training and validation pipelines train and validate a new model using the datasets generated by the data pipeline.

When the validation pipeline confirms the new model isn't worse than the production model, the new model gets deployed.

This process repeats continuously.

---

## During Serving

```
User
 ↓
Product Detail Page (Nike Air Max)
 ↓
Recommendation Service
 ↓
Retrieval
 - anchor item's embedding already precomputed and cached at indexing time.
 - lookup anchor item embedding from cache, query the ANN store.
 - returns 200 candidates + similarity score
 ↓
Ranker
 - country, device read from the request
 - lookup remaining user features (preferred brands, average purchase price,
   historical category affinity) from the online store, keyed by user_id
 - lookup item features (anchor + all 200 candidates) from the online store
 - compute cross features inline (see "Computed Inline" below)
 - score and rank all 200
 ↓
Truncate to top 20 (actual widget display slots)
 ↓
Respond to user
 ↓
Log Impression Event — only for the 20 items actually exposed

All of the above completes under 100ms p99.
```

Feature computation code (cross-feature derivation, lookups) is shared between the serving path and the training-dataset builder, so training and serving compute features the same way. This is what keeps training-serving skew in check — not a separate "feature engineering step," just the same code path used in both places.

To retrain, we need the exact features used during serving. In production, engineers don't recompute features from raw logs on every training run, and we do **not** log every feature value used at serving time — we log the events needed to reconstruct those values later via point-in-time correct joins. That's why we need both an online store (serving) and an offline/warehouse store (training).

---

## What Gets Logged

### 1. Impression Event
`timestamp, user_id, anchor_item_id, recommendation_impression_id, candidate_item_id, position, retrieval_similarity_score, device, country`

- One row per candidate **actually shown** to the user — the top 20 post-truncation, not the full 200 the ranker scored. An item the ranker ranked but never rendered was never exposed, and must not be logged as an impression (it can't validly become a "shown but not clicked" negative for either stage).
- `device` and `country` are logged here so historical values can be reconstructed for training rows, and so device-level Inverse Propensity Scoring (IPS) position-bias correction has the data it needs.

### 2. Click Event
`click_time, user_id, candidate_item_id, recommendation_impression_id`

- References the impression it came from.

### 3. Purchase Event
`purchase_time, user_id, item_id, order_id`

- No recommendation information at write time — just the fact of a purchase. Attribution is decided afterward, as a separate step, never inferred at write time.

---

## Attribution

> **Label Attribution guardrail:** A recommendation-attributed purchase is a purchase occurring within 24 hours of a click on an item in the Similar Items widget.

Applying this rule to a Purchase Event produces:

```
recommendation_attributed_purchase = True | False
```

This join (Click Event + Purchase Event, within the 24h window) is what turns a raw purchase into a labeled outcome the training pipeline can use.

---

## Two Independent Dataset Builders

Both stages read from the same raw logs (Impression, Click, Purchase) but branch into two independent pipelines, because they need different labels and different feature shapes.

```
                Impression Event ──┬── Click Event ────────► Retrieval Dataset Builder
                                   │
                                   └── Attributed Purchase ─► Ranking Dataset Builder
```

### Retrieval Dataset Builder

**Positive:** (anchor_item_id, candidate_item_id) where the candidate was clicked.
**Negative:** (anchor_item_id, candidate_item_id) where the candidate was exposed (logged impression) but not clicked.

**Build:**
1. `Impression Event LEFT JOIN Click Event` on `recommendation_impression_id` + `candidate_item_id` → `label = 1` if a click exists, else `0`.
2. Join the **versioned item catalog** (see below) on `anchor_item_id`, as of the impression's timestamp, to pull anchor features.
3. Join the same versioned item catalog on `candidate_item_id`, as of the impression's timestamp, to pull candidate features.

**Result — materialized in the warehouse:**

| anchor_features (category, subcategory, brand, price_tier, tags, image_embedding, text_embedding) | candidate_features (same set) | label |
|---|---|---|

This table covers **exposure-derived pairs only.** In-batch negatives (other anchors' positive candidates reused as negatives within a training minibatch) are **not** part of this warehouse table — they're constructed dynamically by the training loop at batch-assembly time, since they depend on whatever anchors happen to co-occur in a given random batch.

### Ranking Dataset Builder

**Label:** binary. `1` if `recommendation_attributed_purchase = True` for that (user, candidate) impression, `0` otherwise (covers both clicked-but-not-purchased and shown-but-not-clicked).

**Build:**
1. Start from Impression Event (already scoped to the 20 exposed items).
2. Join `recommendation_attributed_purchase` (from the Attribution step) on `user_id` + `candidate_item_id` + `recommendation_impression_id` → label.
3. Join user behavioral aggregates (preferred brands, average purchase price, historical category affinity) as of the impression timestamp.
4. Join the versioned item catalog for anchor features and candidate features, as of the impression timestamp.
5. Join candidate historical CTR / CVR / impression-count from the daily pre-aggregated candidate stats table (most recent snapshot strictly before the impression date).
6. Compute cross features inline from the anchor and candidate features already in the row (not joined from storage — see below).

**Result — materialized in the warehouse:**

| user_features | anchor_features | candidate_features (incl. historical CTR/CVR/impression_count) | cross_features | label |
|---|---|---|---|---|

## Computed Inline vs. Stored

**Computed inline, not stored:** `same_brand?`, `same_category?`, `same_subcategory?`, `price_ratio`, `price_diff`. These are deterministic boolean comparisons or simple arithmetic over anchor and candidate features that are already present in the row — there's no benefit to persisting them, and no "feature engineering pipeline" is needed. The same derivation code runs in the training-dataset builder and in the online ranker at serving time, so they can never drift apart.

**Stored:** `retrieval_similarity_score`. Unlike the cross features above, this isn't derivable from static item attributes — it's the output of the Stage 1 item encoder at serving time, so it's captured directly on the Impression Event and carried through rather than recomputed.

**Versioned separately (model artifacts, not data pipeline concerns):** the image/text embedding encoders and the item encoder network itself. These represent fitted parameters — if an encoder version changes, every downstream item embedding silently changes meaning, so these are versioned and stored as model artifacts at training/deployment time, not as part of the data flow above.

## Point-in-Time Correctness

Every join above that pulls a historical value is scoped to data available **before** the impression being labeled:

| Source | Feature(s) | Rule |
|---|---|---|
| Purchase Table | Average purchase price, historical category affinity | Aggregate purchases before the impression |
| Item Catalog | Anchor / candidate item features | Versioned catalog — join the row valid **as of the impression timestamp**, not the current catalog state |
| Impression Table | Historical recommendation impressions | Count impressions before the impression |
| Impression + Click | Historical recommendation CTR | `clicks / impressions`, using only data before the impression |
| Impression + Attributed Purchase | Historical recommendation CVR | `attributed purchases / impressions`, using only data before the impression |

**Why the item catalog needs versioning:** price and category can change over time (promotions, re-categorization). A plain current-state join would pull today's price into a training row from three months ago — leaking information the model never actually saw at serving time. The catalog needs an effective-dated (as-of) join, the same discipline already applied to the behavioral aggregates.

**Why CTR/CVR/impression-count are daily snapshots, not per-row exact recomputation:** recomputing these aggregates by scanning the full historical event log for every training row would be prohibitively expensive at 20–100M events/month, and unnecessary — candidate-level click/purchase behavior shifts gradually over days, not within a day, so sub-day precision buys nothing. A daily pre-aggregation job caps staleness at one day and keeps the join cheap. "Point-in-time correct" here concretely means *as of the most recent daily snapshot before the impression*, not instant-level exactness — worth stating outright rather than implying exactness.

**Refresh cadence: daily**, for the same reason — it matches the actual rate of change in the underlying behavior at this traffic scale, and avoids building real-time feature infrastructure before there's evidence it's needed. Revisit if a specific candidate segment (e.g. flash-sale items) shows daily lag is measurably hurting ranking quality.

---

## Note

Because retrieval's exposure-derived negatives are now drawn from the same truncated (top-20) impression log as ranking, retrieval only gets corrective signal on candidates that made it through ranking and were actually shown — not on the other ~180 candidates it retrieved but ranking never surfaced. Worth watching as a potential feedback-loop blind spot once there's production traffic; not a blocker for v1.
